## Conclusion

Two defects are reproduced against the published implementation using offline
browser fixtures. The first can reject an otherwise valid search before saving
any ads. The second truncates larger DOM-fallback searches. Neither proves the
cause of the three October 4 customer failures: their logs and inputs are not
available in the developer Debugging view.

At the time of this original diagnosis, no production changes, deployment, paid
runs, pricing changes or customer messages had been made. Subsequent authorized
repair work and rejected cloud tests are documented in the repair report.

## 1. High priority: unrelated images prevent saving valid ads

Locations: `src/performance.ts:31`, `src/routes.ts:1198`.

The preview gate waits for **every** document image with a rendered box at least
32 by 32 pixels. It includes unrelated images and lazy images far outside the
viewport. If any remains incomplete for five seconds, it throws
`preview_unready`. This happens before parsing embedded ad data or reading the
matching media registry, even when the ad already has valid video metadata.

Offline Chromium reproduction using the actual router and readiness function:

| Scenario | Valid ad data available | Saved | Result |
| --- | ---: | ---: | --- |
| Control, loaded image | 1 | 1 | Completed |
| Same ad, unrelated lazy image 50,000px down | 1 | 0 | `preview_unready` after 5.02s |
| Same ad, unrelated pending image | 1 | 0 | `preview_unready` after 5.03s |

The off-screen image was never requested by Chromium, so simply waiting longer
does not resolve that fixture. Both failing fixtures already contain the ad's
video URL and thumbnail. All external requests are intercepted; no public
website or Apify run is involved.

This error is retried. Repeated rejection with no saved rows can eventually
produce the Actor's failed outcome. This is a confirmed failure mechanism, not
confirmed attribution for any October 4 run.

Recommended repair: prefer scoped structured data when sufficient, and perform
readiness checks only for candidate cards whose DOM media actually requires
hydration. Keep unready cards explicitly incomplete/retryable without blocking
unrelated valid cards. Do not remove video-quality or search-scope checks.

## 2. Medium priority: DOM fallback repeatedly scans only the first 250 cards

Location: `src/routes.ts:662`.

The DOM walk stops after collecting 250 roots before excluding already-saved
ads. On the next scan it finds the same roots and never reaches later cards if
the page retains its earlier cards in the DOM.

Offline result: 300 distinct, matching, loaded cards; requested 300; saved 250;
the final card was not saved; outcome `limited`, reason `stale_scroll`. This
specifically affects DOM fallback, not every structured-data search.

It causes incomplete output, not a failed status in this test. It may prompt
users to retry or stop a run, but no customer behavior is established here.

Recommended repair: bound each batch of *unseen* candidates or use a resumable
scan/queue so later cards remain reachable; retain deduplication, per-search
limits and atomic save/charge behavior. Test beyond 250 cards and across retries.

## Additional risks — not confirmed incident causes

### Limited memory headroom

The last owner benchmark (25 ads, September 30, run `qJxdfvXvK87b63vhH`)
peaked at 942.605 MiB with 1024 MB configured memory. That leaves approximately
81 MiB headroom on the configured 1024 scale. It is not evidence that any
October customer run ran out of memory. Larger representative runs need
measurement before selecting a different memory default.

### Per-search timeout and repeated waits

`src/main.ts:99` sets a 300-second handler timeout. Each scroll in
`src/routes.ts:1112` and `:1120` can wait up to 15 or 10 seconds for network
silence, plus two random 1.5–4 second delays. A larger search can exhaust its
handler budget while still making progress. The installed Crawlee code applies
the handler timeout separately from the Actor's overall run timeout.

This is a static risk, not a reproduced customer timeout. Successful partial
output may be retained and reported as limited/partial; it must not be described
as universally causing a failed Actor status.

### Diagnostic persistence

`FACEBOOK-RUN-SUMMARY` is written once, after `crawler.run()` returns
(`src/main.ts:179`). Hard termination before that point can leave no summary.
Caught top-level crawl errors are reduced to the generic `crawl_error` reason.
Checkpoint aggregate counters and retain a safe fixed error category without
storing customer queries, cookies, URLs or raw sensitive errors.
